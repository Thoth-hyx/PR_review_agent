01

全链路总览

三条入口路径的差别只在前半段——任务怎么被创建、由谁触发执行。汇入 ReviewService._run_review 之后完全一致。

A · 同步审查

调用方阻塞等待报告
  1. ReviewService.create_review
  2. _validate_review / _require_agentic_model
  3. _create_task → store.create
  4. _run_review → ReviewHarness.run

B · 异步审查

立即返回 PENDING,后台线程执行
  1. ReviewService.enqueue_review
  2. _create_task → store.create
  3. TaskQueue.submit → _deliver
  4. _process_queued → _run_review

C · GitHub Webhook

PR opened / reopened / synchronize
  1. handle_github_pull_request
  2. store.claim_webhook 去重
  3. _create_deferred_task 只存 diff_url
  4. _process_queued 里 fetch_diff
路径 C 的区别:建任务时不下载 diff,只把 diff_url 存进任务输入。 真正取 diff 的动作发生在队列消费者 ReviewService._process_queued 里—— 这样 GitHub 的 webhook 超时窗口内不需要等网络下载。
02

异步审查链路

同一个 POST /v1/reviews,加一个 ?async=true 就换一条路(api.py:353)。返回值从 201 变 202,状态从 SUCCESS 变 PENDING,执行从调用方线程挪到队列消费者线程。

前半段完全一样。enqueue_review 把同步路径那 6 个前置校验和 _create_task 原样跑了一遍——diff 在入队前就已经写进 task_payloads 了。差别只在最后一行:同步调 _run_review,异步调 queue.submit。

两种后端

环节redis-streamsmemory-acked
判定self._redis 非空self._redis 为 None
入队XADD evoagent:review:stream直接 ThreadPoolExecutor.submit(_deliver)
消费workers 个 _redis_worker 线程,XREADGROUP 阻塞 1000ms线程池自己跑,无消费者组
重投XADD 回同一个 stream,无退避threading.Timer 延迟后重新 submit,有退避
确认处理完才 XACK无 ACK
崩溃恢复XAUTOCLAIM 认领闲置超 60 秒的消息无,进程挂掉任务即停在 PENDING

后者只适合单进程开发环境。_reclaim_stale 里那句 min_idle_time = lease_seconds * 1000(task_queue.py:126)是毫秒,lease_seconds 默认 60,所以认领阈值是 60 秒。

重试阶梯与死信

max_attempts 默认 3,envelope 里的 attempt 从 0 开始,_deliver 一进来先 +1(task_queue.py:71)。

投递次序attempt判断后果
第 1 次11 >= 3 假退避 2**0 = 1 秒后重投
第 2 次22 >= 3 假退避 2**1 = 2 秒后重投
第 3 次33 >= 3 真进死信

退避公式是 min(2 ** (attempt - 1), 10),封顶 10 秒,只在内存后端生效。Redis 后端失败即 XADD 回队(task_queue.py:81-84),立刻可被重读。

PermanentTaskError 不参与这套阶梯。它在 task_queue.py:75-77 有独立的 except 分支,第一次就进死信,不重试。_process_queued 里两处会抛它:任务行不存在(service.py:343)和载荷不存在(service.py:361)——这两种情况重试多少次都不会变好。

队列重试 = 重跑整个 harness

但代价远低于从头跑。_process_queued 的异常在 service.py:384 被 raise 出去,_deliver 接住并重投;重投后重新进 _run_review,而 ReviewHarness.run 开头有幂等短路(harness.py:69-70),runtime 会跳过 completed 的节点,agentic 会跳过已完成的阶段。已经花掉的模型调用不会重花。

和同步路径的全部差别

同步 create_review异步 enqueue_review
HTTP 码201202
返回体含完整 report{"task_id", "state": "PENDING", "queue"}
diff 入库时机都是 _create_task 里就 save_task_payload,入队前已完成
执行线程调用方线程队列消费者线程
失败处理直接抛给调用方先 releases.observe + alerts.evaluate,再 raise 交给队列
回帖 PR不做github_issue_url 有值且 auto_post_review 为真时做

GitHub Webhook 链路

这条路径不走鉴权主体,靠 HMAC 签名自证身份。请求进来先过 7 道关卡,再登记一个「只存 URL、不存 diff」的延迟任务。

七道关卡

#检查位置不通过时
1X-GitHub-Event 等于 pull_requestapi.py:369202 ignored
2github_webhook_secret 已配置api.py:372503
3X-Hub-Signature-256 验签通过api.py:375401
4pull_request.updated_at 在重放窗口内api.py:386409
5delivery_id 未被用过store.py:920返回 duplicate,不建任务
6action 属于三个白名单值service.py:426202 ignored
7repository / number / diff_url 齐全service.py:434ValueError
第 4 关用的是 abs(...)。api.py:386 算的是 abs(now - updated_at)——事件时间无论在窗口之前还是之后,只要偏离超过 webhook_max_age_seconds 一律拒。既挡重放,也挡时钟漂移到未来的畸形事件。

三层幂等

层机制挡什么
1webhook_deliveries.delivery_id 唯一约束,INSERT 成功即抢占同一个 delivery 被投两次,建出两个任务
2重复时比对 payload_sha256delivery_id 被复用于不同内容——直接 ValueError
3upsert_comment 正文里的 <!-- evoagent-review:task_id -->回帖被重放,PR 上出现重复评论

第 1 层与第 2 层合起来是一次比对:先试 INSERT,撞唯一约束说明 delivery 见过,再取出已存的摘要跟本次比。摘要相同 = 真正的重复投递;不同 = 有人拿旧 delivery_id 塞了新内容,这是异常,直接抛。

延迟任务:只登记 URL,不下载 diff

_create_task(同步 / 异步)_create_deferred_task(Webhook)
入参拿到完整 diff 字符串只拿到 diff_url
落库调 save_task_payload 存 diff不调,只写 diff_pending: True
校验入口处 _validate_review推迟到 worker 里做

补下载发生在 _process_queued(service.py:346-359),七步:

#动作
1store.get_task_payload(task_id) 拿到 None
2github_client_for_installation(installation_id) 取回带安装令牌的客户端
3ensure_repository_access(repository) 校验访问权限
4fetch_diff(diff_url) 下载
5_validate_review(repository, diff) 补做入口跳过的校验
6save_task_payload 落库
7update_task_input 写回 diff_pending: False、diff_bytes、diff_sha256
为什么要延迟。下载 diff 是网络动作,放在 webhook 的请求线程里会让响应时间不可控。请求里只登记 URL 并把 diff_url 一起塞进队列消息,把下载推到 worker——请求路径上只剩一次数据库写入和一次入队。

租户从哪来

Webhook 没有登录用户,租户要靠三级兜底(service.py:414-416):

顺序来源何时命中
1调用方传入的 tenant_id内部转发或测试
2store.installation_tenant(installation_id)GitHub App 安装记录里查得到
3settings.default_tenant_id前两级都空

路径 C 没有复用 enqueue_review,而是在 handle_github_pull_request 里自己走了一遍校验和入队。差别是它用 _create_deferred_task,且把 _validate_review 推到 worker(此刻还没有 diff 可校验)。返回体里多一个 will_post_to_github,值就是 auto_post_review。

04

harness 三个节点

ReviewHarness.run 把三个方法包成 RuntimeNode 交给 AgentRuntime.execute。节点之间不互相调用,靠一个共享字典传值。

顺序节点名handler 方法读 state 的键返回的增量写了什么
1 planning ReviewHarness._planning diff {"parsed": …} PLANNING store.transition
2 executing ReviewHarness._executing parsed diff task_id repository {"findings": […]} EXECUTING store.transition
3 reviewing ReviewHarness._reviewing parsed findings {"report": …} REVIEWING store.transition

状态机与合法转移

ReviewHarness._transition 按 ALLOWED 表校验每一步转移,并把进度写进 tasks.state 与 trace_events。目标态等于当前态时直接返回——这是节点重试时命中幂等分支的情况。

reviewing 节点里的 collaboration 从哪来

_reviewing 组装 ReviewReport 前会先取协作摘要,这里有两条路,先走哪条由鸭子类型决定。

顺序条件取值来源
1 reviewer 上有 collaboration_summary 方法且返回非空 AgenticReviewer.collaboration_summary——本次运行刚结束,数据还在内存里,顺带把 run_mode、components、execution 也一起取出来
2 否则回落到 self._persisted_collaboration_summary 读 store.get(task_id)["collaboration"],也就是 agent_messages 表
第二条路当前恒为空。它读的 agent_messages 表由 store.record_agent_message 写入,而全仓库没有任何地方调用这个方法——所以 _persisted_collaboration_summary 永远在读一张空表,返回 {}。它声称的协议名 plan-challenge-revise-evidence-verify-arbitrate 在仓库里也没有生产者;当前引擎实际用的是 lead-workers,由 collaboration_summary() 产出。这段代码是留给旧协议的读侧残留。
05

runtime 的节点循环

AgentRuntime.execute 不知道任何业务,只做四件事:按序调 node.handler(state)、合并返回值、每步前查预算与取消、每个节点成功后写检查点。

循环中的动作代码位置说明
恢复检查点AgentRuntime.execute节点状态为 completed 时把上次的增量合并回字典,跳过 handler
预算与取消闸门AgentRuntime.execute 内的 guard每次尝试前调 store.is_cancelled,并检查步数与单调时钟
调用节点node.handler(state)回调进 harness 的 _planning / _executing / _reviewing
合并与落盘AgentRuntime.executestate.update(output) 后调 store.save_checkpoint
重试AgentRuntime.execute 内层循环失败也消耗步数并写一条 failed 检查点;成功则 break
事件与追踪AgentRuntime.execute 内的 emit发出 RuntimeEvent;OpenTelemetry span 由 harness 的 _span 提供
三处不重试的异常:ValueError、RuntimeCancelled、RuntimeBudgetExceeded 直接穿透重试循环,一路抛到 ReviewHarness.run 的 except,由它落成 FAILED 或 CANCELLED。

executing 节点内部:agentic 七阶段

整个多智能体协作发生在 ReviewHarness._executing 调用的 AgenticReviewer.review_with_context 里面。它是一张阶段表:每个阶段跑完就把结果写进 session 字典并存检查点。

#阶段入口方法模型产出写进 session 的键
0装配与记忆召回AgenticReviewer._review_with_context无不写 session;产出 memory_context 传给后续所有阶段
1扫描AgenticReviewer._scan无scanner_complete scanner_findings scanner_components
2委派AgenticReviewer._run_lead("delegate")LLM 1delegations risk_level lead_delegation
3worker 并行AgenticReviewer._run_pending_assignments每 worker 一轮worker_results
4评估返工要求AgenticReviewer._run_lead("assess-workers")LLM 2lead_assessments
5返工一轮AgenticReviewer._run_pending_assignments(round=1)worker 再跑revision_results revision_rounds
6盲审AgenticReviewer._run_criticLLM 3critic_decisions critic_candidates critic_complete
7终审AgenticReviewer._run_lead("finalize")LLM 4lead_final accepted_findings stop_reason

单角色循环 BoundedRole.run

阶段 2 到 7 里每一次模型交互,都由 BoundedRole.run 驱动。Lead 与 Critic 拿到的是空工具表,worker 拿到按角色白名单过滤后的工具表。

每轮顺序调用结果
1working_memory_supplier()任务内工作记忆,注入到 payload 的 working_memory 键
2ContextManager.build_managed_context按预算压缩 payload 与历史观察
3JsonChatClient.complete_json唯一的模型调用点
4ToolRegistry.invoke仅当动作是 tool;失败也记成一条观察喂回下一轮
5动作分发final 时把观察列表挂在 _observations 上返回;其它值抛 ValueError
退出条件:动作返回 final,或 max_steps 用尽后抛 RuntimeBudgetExceeded——后者会穿透 runtime 的重试,直接让整个任务失败。

08

中断之后:重跑时跳过了什么

恢复不是一段独立的代码,而是同一条路径再跑一次。两层检查点各负责一半:外层跳过整个节点,内层跳过已完成阶段。

崩溃位置重跑时的行为省下的模型调用
planning 节点内 load_checkpoints 无 completed 记录 → 三个节点全部重跑 无
executing 早期(扫描后、委派前) planning 被跳过;_load_lead_session 恢复 session,scanner_complete 为真 → 从委派继续 扫描
worker 并行期间 已完成的 worker 留在 worker_results 里,_run_pending_assignments 只调度缺的那些 已完成的 worker 那一轮
critic 阶段 delegations 与 worker_results 都在 → 从 _run_critic 继续 委派 + 全部 worker
succeed 之前(task 仍是 REVIEWING) 三个节点检查点都是 completed → 三个 handler 一个都不执行,直接组装报告 全部
两层为什么必须都在:runtime 的重试会把 executing 节点整个重跑一次。若没有内层的 session 检查点,每次重试都要重新走一遍扫描、委派和两个 worker;有了它,重试的代价降到"只剩没做完的那几个阶段"。

三条旁路:取消、死信、回帖

主链路之外还有三条支线,都不经过节点循环的正常返回路径。

取消 · 轮询式,不是中断式

步骤位置动作
1ReviewService.cancel_task调 store.request_cancel,置 cancel_requested = 1
2AgentRuntime.execute 内的 guard下一次节点尝试前调 store.is_cancelled,查到则抛 RuntimeCancelled
3runtime 的 non_retryable取消异常穿透重试循环,不重试
4ReviewHarness.run 的 except TaskCancelled调 store.cancel,状态落 CANCELLED,再向上抛
它不会打断正在进行的调用。检查点只在节点尝试之前,所以一次已经发出的模型调用或工具调用会跑完;取消在下一个边界生效。

死信 · 队列投递彻底失败

步骤位置动作
1TaskQueue._deliver投递失败,或尝试次数超过 queue_max_attempts
2TaskQueue._dead_letter存入死信表,回调服务层
3ReviewService._on_dead_letter任务若还不是终态则 store.fail,并 store.create_alert 一条 critical 告警
4ReviewService.resume_task / TaskQueue.replay_dead_letter人工重新入队

回帖 · 只有异步路径和 Webhook 路径会做

条件位置动作
payload 带 github_issue_url 且 settings.auto_post_review 为真ReviewService._process_queued调 github_client_for_installation 取客户端,再 upsert_comment 把 to_markdown(report) 发到 PR
同步路径 create_review—不回帖,直接把报告返回给调用方
幂等标记:回帖正文里带一个 <!-- evoagent-review:<task_id> --> 注释,upsert_comment 靠它找到已有评论并更新,而不是重复发帖。

附:这些对象什么时候被造出来

图上出现的每个对象都有明确的构造时机。按生命周期从长到短排列。

时机位置造出什么
进程启动一次 ReviewService.__init__ store、MemoryManager、ContextManager、SkillRegistry、JsonChatClient、AgenticReviewer、ReviewHarness、TaskQueue
启动时 + 每次 reload_skills ReviewService._build_agentic_reviewer 把 15 个依赖装进 AgenticReviewer;扫描器列表在这里过滤掉了 OpenAICompatibleReviewer,并读出生效中的提示词与结构化配置
每个任务一次 ReviewService._create_task task_id(uuid4)、tasks 行、diff 载荷
每次执行一次 ReviewHarness.run 共享字典 state、线程本地的 _ctx 游标
